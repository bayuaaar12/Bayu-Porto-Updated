PLATE 03.A · WARUNG PINGKAL

Smart Face Recognition POS & Member System

Problem
At a culinary MSME, member discounts died at the cashier: staff typed a phone number, guests waited, the queue grew. A loyalty program that adds friction is not a loyalty program.
Decision
Do not bet on one detector. Haar Cascade locates a face in the frame; ORB covers messy lighting with classical features; DeepFace (Facenet512) supplies embeddings when we need a match we can store. Laravel exposes a REST endpoint for base64 image payloads so the Python pipeline never has to own the POS UI. MySQL keeps member records next to tickets — one checkout, not two systems taped together.
Result
Checkout time down ~40%. The cashier looks up, not down. Source for the dual-method pipeline is archived with the Laravel POS (no face images in the public dump).

PLATE 03.B · ENTERPRISE COUNTER

Enterprise Point-of-Sale Web Platform

Problem
A full-featured web POS is easy to demo and hard to keep honest at noon rush: stock lies, sales reports hitch, the next ticket waits on a query that should have been an index.
Decision
PHP/Laravel as the system of record. Real-time inventory and sales tracking on MySQL, with query plans and indexes treated as product work — not a later “optimisation sprint”. JavaScript on the counter UI stays thin; the database does the heavy lifting.
Result
Transaction speed and data retrieval up ~35% after indexing and query cleanup. Cashiers get the next SKU without watching a spinner.

PLATE 03.C · FINTECH

Investkan — Crowdfunding

Problem
Retail investors in Indonesia do not lack enthusiasm; they lack a single, readable door into deals across F&B and technology. Spreadsheets and WhatsApp groups do not scale.
Decision
A Laravel/PHP application with MySQL as the book of record: listings, sectors, and investment flow in one place. JavaScript only where the listing UI needs to filter without a full reload. Trust is copy and schema — campaign fields, not a gradient.
Result
A working crowdfunding surface for discovering and placing funds across sectors. (Live URL still to be attached.)

PLATE 03.D · FRONT OF HOUSE

Interactive Restaurant Menu

Problem
Printed menus go stale the week the kitchen changes a price. Guests still filter by “under 50k” and “bukan pedas” with a finger on paper.
Decision
A React SPA: category and price filters as first-class state, dishes from a REST API so the kitchen can change a plate without a rebuild. Responsive because the phone at the table is the real viewport.
Result
A menu that behaves like software — filter, fetch, sit down — instead of a PDF with rounded corners.
